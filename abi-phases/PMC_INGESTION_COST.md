# What it would cost to run PubMed Central through our ingestion

Measured and priced on 2026-11-19. "Our ingestion" is the pipeline as it is
today: the PubMed Library downloads PDFs from the PMC Article Datasets on AWS
(`pmc-oa-opendata`), and Phase v2 renders each PDF to markdown, cuts 512-word
windows overlapping by 128, sends every chunk through each of the 8 current
prompts with one model, and projects the results to Fuseki (triples) and
Qdrant (vectors of chunks and of extracted items, `text-embedding-3-large`,
3072 dimensions).

The tables between `<!-- table:… -->` markers are generated by
`scripts/pmc_ingestion_cost/cost_model.py` from the committed measurements,
`prices.yaml` and `assumptions.yaml`: change a price and run
`cost_model.py report` to regenerate them (`make test-pmc-cost` fails while
they are stale). Each per-paper figure says where it came from:

- **prod**: read-only queries on production (294 papers, 7,441 chunks);
- **sample**: a seeded random sample of PMC (3,000 articles' metadata, 1,000
  texts, 200 PDFs rendered by our own renderer);
- **calibration**: paid model calls through our extraction adapter, 10
  production chunks × 8 prompts × each model, plus 40 chunks of random PMC
  papers for the cheaper models;
- **offline**: token counts of our own prompts and tool schemas over 400
  production chunks.

PMC adds about 97,000 articles per 30 days (12-month mean, by the date an
article went live in PMC), about 83,000 of them open access. The PMC Cloud
bucket agrees: 87,500 articles appeared in it between two of its daily
inventories 30 days apart. Our PubMed Library reaches only what the bucket
distributes as PDF. That is 99% of the open access subset and none of the
author manuscripts outside it (license table below). The open access subset is
therefore the headline, and all of PMC is the reference.

## Headline: cost per model, PMC open access subset

gpt-4.1-mini, the model every production extraction used so far, is being
retired. OpenAI's deprecations page lists "Jan 14, 2027 | GPT-4.1 mini
(gpt-4.1-mini-2025-04-14) | Deprecated | gpt-6-luna | Oct 14, 2026"
([source](https://developers.openai.com/api/docs/deprecations), read
2026-11-19). It stays in the tables as the measured reference only. Its
announced replacement is **gpt-6-luna**. The same page retires gpt-5-mini
sooner, on **2026-12-11**, in favour of gpt-6.1-terra, so that model is priced
too.

Neither replacement works with our adapter as models are built today. Through
Chat Completions, the endpoint LangChain's `ChatOpenAI` uses, OpenAI answers
our forced tool call with HTTP 400: "Function tools with reasoning_effort are
not supported for gpt-6-luna in /v1/chat/completions. To use function tools,
use /v1/responses or set reasoning_effort to 'none'." Both ways out were
calibrated:

- **effort none**: `reasoning_effort="none"` on Chat Completions;
- **Responses**: default effort over the Responses API (`use_responses_api=True`).
  This route also refuses `temperature`.

Reading the headline:

- **Model calls are the backfill.** The spread between models is about 90×.
  The cheapest is GPT-6 Luna at effort none, at about $0.18M for the open
  access subset. gpt-4.1-mini as production runs it is about $0.68M, and
  Gemini 3.1 Pro (preview) is about $16.5M. Embeddings add about $20k whatever
  the model.
- **Reasoning is what makes a model expensive.** gpt-5-mini and Gemini 3.1 Pro
  spend 850–900 reasoning tokens on each call, against 34–102 output tokens for
  the configurations that do not reason (calibration table). The Responses
  route of the two replacements reasons a little (43–70 tokens per call).
- **Anthropic bills about 700 more input tokens per call** for the same prompt
  (about 1,960 against 1,250 at OpenAI), which is the tool-use preamble.
- **Each month, storage and hosting cost more than the new papers.** A month of
  new papers costs from about $1,800 (Luna) to $164k (Gemini) in model calls.
  Self-hosted, the bill is Qdrant's RAM: production keeps the 3072-dimension
  vectors in RAM, which here takes 30 to 79 r7i.16xlarge nodes, or $95k to
  $246k a month. The managed column bills vectors by stored GB on S3 Vectors
  instead of by RAM.
- **Models differ in how much they extract, and so in what is stored.** On
  PMC text, gpt-4.1-mini returns about 255 items per paper, the replacements
  and Claude 84–147. Most of the difference is the six `solitude_*` prompts:
  on papers that are not about solitude, the newer models return nothing,
  while gpt-4.1-mini still extracts something.

Self-hosted is AWS on-demand in us-east-1. Qdrant runs on r7i.16xlarge nodes
(512 GiB) sized by Qdrant's capacity formulas, with vectors in RAM as
production keeps them. Fuseki runs on one r7i.8xlarge, and the app stack on one
m7i.2xlarge. EBS gp3 holds the Qdrant and Fuseki volumes, and S3 holds the
PDFs, markdown and DuckLake files. Managed is Amazon Neptune for the triples
(db.r6g.8xlarge, I/O-Optimized storage) and Amazon S3 Vectors for the vectors,
with the same AWS app stack and S3. Qdrant Cloud publishes no unit prices: it
bills "CPU, memory, and disk storage usage" through a calculator only. A quote
from it can be put in `prices.yaml` (`managed.qdrant_cloud.usd_per_gb_ram_month`)
and the managed column then prices Qdrant Cloud instead.

How each column is worked out:

- **Production's measured rate**: production's extraction rate over 36 runs
  since the 20-worker pool landed.
- **20 workers, latency only**: what the same pool would do if each call took
  only the calibration's measured latency.
- **Rate limit**: OpenAI's published tokens- and requests-per-minute for each
  usage tier (Build, Launch, Grow, reached at $5 / $100 / $500 of credit
  purchases), used at 70%.
- **Batch queue**: one full batch queue per 24 hours, the most the Batch API's
  enqueued-token limit allows.
- **Grow's usage limit**: the backfill's model-call spend at $200,000 a month,
  Grow's monthly usage limit. Batch halves the spend, and so this time.
- **³ Embeddings at tier limit**: chunks and items at `text-embedding-3-large`'s
  Launch-tier limit.

The account's tier is not visible from here. OpenRouter publishes no
platform-level cap for paid models ("no platform-level request cap"), so its
rows are blank. Its Batch API follows "the batch limits of the upstream
providers".

### Batch API

The pipeline does not use a Batch API today: every call is synchronous. OpenAI's
Batch API and OpenRouter's (`:batch` model variants, "typically 50% of the sync
per-token price") halve the model-call price; see the "… with Batch" columns.
Each batch completes within 24 hours, and OpenAI counts a batch's input tokens
against a per-model queue limit when it is submitted. At the Launch tier that
queue is too small for a backfill of this size; at Grow it takes months (the
time table).

## Method

**PMC facts.**

- **Counts** come from NCBI E-utilities `esearch db=pmc` with `rettype=count`.
  `all[filter]` gives all of PMC and `open access[filter]` the open access
  subset. The seven Creative Commons license filters are grouped as PMC groups
  its subset: commercial use (CC0, BY, BY-SA, BY-ND) and non-commercial (BY-NC,
  BY-NC-SA, BY-NC-ND). The open access articles under none of these are
  "other". Author manuscripts are counted with `author manuscript[filter]`.
- **Growth** is 12 consecutive 30-day windows ending 2026-11-18, each counted
  on `[PmcLiveDate]` (the date an article went live in PMC), for all of PMC
  and for open access.
- **Bucket figures** come from the bucket's own daily S3 inventory (snapshot
  2026-11-18), compared with the snapshot of 2026-10-19.
- **Licenses and PDFs in the bucket** come from a seeded random sample (seed
  855) of 3,000 articles from that inventory, each read from its
  `metadata/<PMCID>.<version>.json`.
- **NCBI etiquette:** at most 3 requests per second and a `tool` name; the
  script sends `NCBI_EMAIL` as the contact address when it is set.

**Paper length.**

- **PMC's text:** the first 1,000 sampled articles, using each article's
  `.txt`.
- **PDFs:** the first 200 sampled articles with a PDF. Each was rendered by our
  own `PdfTextRenderer` and cut by our own `WindowChunker(512, 128)`.
- **Counts:** words are whitespace-separated; tokens are `o200k_base` (model
  calls) and `cl100k_base` (embeddings).
- **Render timing:** CPU time per PDF on an 8-core Intel Xeon Platinum 8259CL.
  The renderer's layout model uses several cores, so CPU time exceeds wall time.

**Per paper, per model.**

- **Calls:** chunks per paper (rendered sample) × 8 prompts. Each extraction
  costs the calibration's calls per extraction (retries included). OpenRouter
  routes carry its 5.5% credit fee.
- **Input tokens per call:** our offline count of each prompt (template
  rendered over 400 production chunks, plus the tool definition), plus the
  model's measured overhead. The overhead is the billed tokens minus the offline
  count on the calibration's own chunks: about 0 for gpt-4.1-mini, +74 for the
  GPT-5/6 family and +760 for Claude.
- **Output tokens and items:**
  - A model calibrated on chunks of random PMC papers uses those means.
  - The others (gpt-5-mini, Sonnet, Gemini) were measured only on production's
    chunks, whose papers were chosen for their topic. They are scaled through
    gpt-4.1-mini, which ran on both. Their items are gpt-4.1-mini's PMC items
    times their item ratio to it on production's chunks. Their answer text (not
    their reasoning) shrinks by gpt-4.1-mini's PMC-to-production output ratio.
- **Embeddings:** each chunk's `cl100k_base` count, plus each item's (the mean
  per prompt over production's items), at `text-embedding-3-large`'s price.
- **Storage** is computed from production's measured rates:
  - Qdrant bytes per vector, on disk, payload and index included (14,373);
  - Fuseki bytes per triple (1,937);
  - DuckLake bytes per row of each table;
  - triples as the graph projection writes them: 2 per paper, 5 per chunk,
    5 per extraction and 7 per item. This reproduces production's count exactly.
- **Qdrant RAM** uses Qdrant's capacity formulas: the vector, plus
  `m × 2 × 4 × 1.2` bytes of HNSW, plus a 52-byte ID tracker, plus 20% headroom.
  Nodes = RAM / (80% of the node's memory).

**Time to complete.** The production rate is the mean over every extraction run
since the 20-worker pool landed (2026-09-11) that made at least 200 calls.

## Assumptions and uncertainty

The assumptions are in `scripts/pmc_ingestion_cost/assumptions.yaml`; each can
be changed and the tables regenerated.

- **Calibration size.** 10 production chunks per model, and 40 PMC chunks for
  five configurations (26 for the two Responses ones, where the run's cap
  stopped it). The 90% ranges in the headline are a bootstrap over the
  complete chunks of whichever of those runs a model's figures come from.
- **Failed extractions** count as no items. The calibration had none: every
  extraction it attempted succeeded.
- **Items and vectors depend on the text and the model.** This is the largest
  uncertainty in storage. Production's papers were chosen for their topic, so
  they hold more of what the prompts ask for. On them, gpt-4.1-mini returns
  about 32 items per chunk; on random PMC papers it returns 14. A
  topic-filtered subset will look more like production. The table below sets
  the two levels side by side.
- **Scaled models.** For gpt-5-mini, Sonnet and Gemini, PMC-level items and
  answers are scaled through gpt-4.1-mini (see Method). On production's chunks,
  Sonnet returned 0.58× gpt-4.1-mini's items in calibration. On the 694 chunks
  Sonnet already ran on in production, it returned 1.4× as many. The ratio
  changes with the text.
- **Prompt caching** is not assumed. Our templates put the instructions before
  the chunk, but the shared prefix is shorter than the 1,024 tokens OpenAI
  needs to cache. Only 13 of the calibration's 2,492 calls were billed any
  cached input, and those are counted as measured.
- **Fuseki's bytes per triple** come from a TDB2 store that has never been
  compacted, so they are an upper bound. Neptune's storage is priced with the
  same bytes per triple, as a proxy: Neptune publishes no size per triple.
- **Sizing.** Self-hosted node types, the Neptune instance and the 20% disk
  headroom are choices, not measurements. On-demand list prices are used,
  with no reserved or savings-plan discount. Query costs for S3 Vectors are
  left out: they depend on use.
- **Rendering time** was measured on the devbox CPU. Production is a burstable
  t3.xlarge, with 4 vCPUs.
- **Rate limits.** The account's OpenAI tier is not visible from here, so every
  tier is shown and 70% of each limit is assumed usable. OpenRouter publishes
  no platform cap for paid models; its upstream providers' limits apply.
- **Gemini 3.1 Pro is a preview model.** Its price and behaviour may change.

## What would have to change for a full run

These are findings, not plans.

1. **Extraction throughput.** Production makes about 1,000 extraction calls an
   hour. If each call took only the provider's measured latency, its 20 workers
   would make about 60,000 an hour with gpt-4.1-mini, and about 6,000 with the
   reasoning models (gpt-5-mini, Gemini). For the open access subset that is
   about 130 years at today's rate, against about 2 years latency-bound. The gap is in writing each
   extraction to DuckLake, whose commits serialise (#635). A full run needs
   extractions written in batches, or in a store that takes concurrent writes.
2. **A working replacement for gpt-4.1-mini, before 2027-01-14.** gpt-5-mini
   goes sooner, on 2026-12-11. Neither replacement accepts our forced tool
   call through Chat Completions unless reasoning is off. Adding them as the
   catalog adds OpenAI models today would fail every call. They need
   `reasoning_effort="none"` or the Responses API (without `temperature`).
3. **Batch.** No route in the pipeline uses a Batch API. Batch halves the price
   of model calls on OpenAI and on OpenRouter (`:batch` variants). On OpenAI,
   the queue limit then decides the pace: a full queue every 24 hours is about
   3 months for the open access subset at the Grow tier, and years at Launch.
4. **Provider tier and spend limit.** Through the synchronous API, the open
   access subset takes about 5 months at OpenAI's Launch rate limits and about
   6 weeks at Grow's. Grow starts at $500 of credit purchases. Its monthly
   usage limit, $200,000, then sets the pace for every OpenAI model except
   Luna. gpt-4.1-mini's backfill takes at least 3 months at that spend, and
   gpt-6.1-terra's about 9, unless OpenAI raises the limit (time table).
5. **Vector storage.** Kept in RAM as production keeps them, 3072-dimension
   vectors for the open access subset need tens of 512 GiB nodes. Binary
   quantization (originals on disk), fewer dimensions, `text-embedding-3-small`,
   or embedding chunks only each cut that several-fold (embedding scenarios).
   Item vectors outnumber chunk vectors about 15 to 1 for gpt-4.1-mini.
6. **The triple store.** A full run is 12 to 22 billion triples, or 23 to 42 TB
   at production's bytes per triple, on one TDB2 store that has never been
   compacted. That is beyond one Fuseki on one disk. On Neptune it fits the
   128 TiB cluster volume, but the instance size is a guess.
7. **PDF rendering.** About 35,000 CPU-hours for the open access subset: a
   year and more on production's 4 vCPUs, a few months on one 16-vCPU worker.
   PMC's own text needs no rendering and gives the same number of chunks per
   paper (PMC-text scenario).
8. **Production's disk.** Production holds about 38 MB per paper across its
   stores and has 34 GB free: room for roughly 900 more papers. Two stores
   grow without bound: DuckLake keeps about 9× its live data in old snapshot
   files, and Fuseki has never been compacted.

Production received only read-only queries. DuckLake was attached `READ_ONLY`
and queried with `SELECT`s. Dagster's event log was read inside a `READ ONLY`
transaction. Qdrant answered collection-info `GET`s, and Fuseki a SPARQL
`SELECT`. `du` and `docker stats` were also run. The calibration ran in the
API container, reading the provider keys from its `.env` in memory. It did not
start the engine, because an engine start publishes declarations into the
datasets. It wrote nothing to any dataset, queued no run, and restarted no
service. The one file it put in the container's `/tmp` (the PMC chunks it
sent) was removed afterwards.

These runs predate the calibration script's present budget rules: the
provider client could retry on its own, a failed request was charged nothing,
and each run's cap was chosen by hand to keep the total under 5 USD. Their 64
failed requests are all HTTP 400 rejections of the request's parameters,
refused before any generation, and none timed out, so the spend above stands.
The script now enforces one 5 USD budget across runs (`--already-spent`),
charges a failed request its worst case, and leaves retrying to the
pipeline's own retry policy.
